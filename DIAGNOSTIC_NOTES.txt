1402zo: where the screen stops is not where the console stops
  The 14.02 run that ended at "PROOF-OK syscall-page-needs-stub" painted
  nothing from afterglow. That does not put the death at the hand-off: from
  afterglow's first line to its first ring-0 shot there is no yield, and a
  DOM write does not reach the screen until the thread yields. The stub,
  pin, interlock, libc, gadget and shooter lines all sat in the DOM when the
  console died inside the first shot, so the jb stage's STUBS line was the
  last thing the screen had ever received.

  What this build adds (diagnostic only):
    - the deadman clock starts at the first afterglow line, with a 150 ms
      forced frame before any kernel work: "ALIVE 0.15 s | pre: stubs"
    - phase beats: pre: stubs seeded, pre: pinned core N, pre: interlock
      clear, pre: gadgets ok, pre: shooter ready
    - a forced frame BEFORE the first shot ("FIRE leak shot") and before
      the [1b] scan shot ("FIRE scan shot"), then "leak returned" /
      "scan returned" after each returns
    - jb-g.js paints "handing over to afterglow..." in the status line and
      yields 150 ms before the dynamic import, so even a death during
      module load leaves a named phase
  Everything else -- gate, [7b] pass, uid 0, teardown, payload tables and
  the dbgstop gate disarm -- is unchanged from 1402zn.

  How to read the run:
    freeze at "pre: stubs"           -> died in seedStubs or the syscalls
                                        before pinning; no ring-0 shot
    freeze at "pinned core N"        -> died between pin and libc
    freeze at "interlock clear"      -> died finding libc or checking gadgets
    freeze at "gadgets ok"/"shooter" -> died building the shooter
    freeze at "FIRE leak shot"       -> died INSIDE the first kernel shot;
                                        the console took that chain down
    freeze at "leak returned"        -> the first shot came back; death is
                                        in the leak analysis or the [1b] shot
    freeze at "FIRE scan shot"       -> died inside the gadget scan shot
    clock still counting, no new    -> main thread alive, something else is
    log lines                          stuck; note the seconds and report
    jb STUBS line with no ALIVE ...  -> died before the import yielded;
                                        report which jb line is last

1402zn: the debug-settings stop test
  What it is for: prove the rcmgr debug-menu patch actually makes the hidden
  Debug Settings entry appear in Settings, WITHOUT loading any payload and
  WITHOUT leaving anything running that could crash the console while the
  user walks to Settings or closes the browser.

  How to reach it: go-dbg.html -> launch.html?...&mode=dbgstop
    (same chain, same patches, same teardown as kpstep -- no kpayload, no
    dump, no payload call, no payload step chain)

  What it does, in order:
    1. the normal chain: WebKit stage, gate, [7b] patch pass, uid 0,
       handle teardown -- byte-for-byte the same kernel work as 1402zm
    2. the rcmgr debug-menu pass (inherited from Andrewtes):
         pass 1 scans kernel text [kbase, kbase+0xCFE880) for the qword
                "rcmgr_de" and checks the tail bytes are "bug"
         pass 2 scans data [kbase+0x1520000, +0x700000) for a pointer to
                that string; handler = *(hit+8)
         reads 80 bytes of the handler, finds the first e8 (CALL) whose
         byte +5 is 85 (TEST) -- the permission check -- and patches its
         call target with b8 01 00 00 00 c3 (mov eax,1; ret)
    3. READ-BACK: k.read(target, 6) must return exactly b8 01 00 00 00 c3.
       Only then does the run print DEBUG MENU PATCH CONFIRMED -- SAFE STOP.
    4. DISARM: the bootstrap saved the original sysent[11].sy_call in the
       kernel header NOP pad at kbase+0xab8 (0xab4..0xab7 carries the gate,
       0xb00+ is real code). The run writes those 8 bytes back to
       kbase+0x1102d88 / 0x1102d8c and reads them back inside the SAME
       ring-0 entry -- once they land, syscall 11 goes to its real handler
       again, and that body is the last one that can ever run through the
       gate. This is what makes closing the browser safe.
    5. deadHalt freezes the status clock and clears its timer. attempt()
       returns immediately: no final messages, no dump block, no payload.
       jb-g.js has already cleared its 45 s watchdog and its 500 ms RAM box
       interval, so the page is inert.

  The gate stash in the bootstrap (14 bytes, new in 1402zn):
      48 8b 81 88 2d 10 01   mov rax, [rcx+0x1102d88]   ; original sy_call
      48 89 81 b8 0a 00 00   mov [rcx+0xab8], rax       ; into the NOP pad
    It runs right after CR0.WP is cleared, before the gate is planted, so it
    always reads the pre-exploit value. Bootstrap is 156 bytes (0x9c), the
    gate stub starts at 0xa0 -- four bytes of room left, do not grow it
    further without moving GATE.

  Success screen (tail):
      debug menu enabled -- go to Settings
      [gate] syscall 11 disarmed -- sy_call restored to 0xffffffff9...
      ========================================
        DEBUG MENU PATCH CONFIRMED -- SAFE STOP
        Open Settings and look for Debug Settings.
        No payload was loaded; nothing else will run.
        The syscall-11 gate is disarmed too -- exit is safe.
        You can close the browser now. Cold boot when done.
      ========================================
      status line frozen: STOPPED -- SAFE TO EXIT

  Failure screen (tail):
      [dbg] rcmgr patch write did not stick
      [dbg] DEBUG MENU PATCH FAILED -- nothing more will run
      status line frozen: STOPPED -- PATCH FAILED
    Earlier [dbg] lines name the exact stage that failed:
      rcmgr_debug_menu string not found in text  -- text scan missed
      rcmgr_debug_menu string tail mismatch      -- lookalike string
      oid_name pointer not found in data         -- pointer scan missed
      oid_name handler pointer is null           -- struct layout differs
      oid_name handler outside text              -- bad pointer
      handler read failed                        -- read fault
      no CALL+TEST in handler                    -- check pattern moved
    In every failure case the kernel work before the rcmgr pass already
    succeeded (uid 0 etc.); the console is safe to power off normally.

  Gate-disarm failure lines (the stop still happens):
      [gate] stash read failed -- gate stays armed
      [gate] no saved sy_call -- gate stays armed
      [gate] saved sy_call 0x... is not a text pointer -- not restoring
      [gate] restore body did not run -- gate stays armed
      [gate] restore read back mismatch -- gate stays armed
      [gate] the gate is STILL ARMED -- if exit crashes, hold power until off
    The "is not a text pointer" case includes a boot that was already patched
    before this build: the stash then holds the gate address itself and is
    rejected on purpose. A stash of all zeros means the bootstrap that armed
    this boot predates 1402zn (page reloaded with new files, no power cycle).

  If the console STILL panics when the browser is closed after a successful
  dbgstop run (status SAFE TO EXIT, restore confirmed), the syscall-11 gate
  is not the cause: the remaining suspects are the applied text patches and a
  foreign call path that hit the stale gate bytes at 0xab4. Report the full
  log line order and the status line.

  Note: the rcmgr patch is a kernel TEXT write that persists until a full
  power-off, exactly like the rest of the patch set. One armed run per boot.

1402zm background (still valid; kpstep path unchanged)

Why 1402zm exists
  The 1402zl run printed
      [kp] tram built (82 bytes), firing now
  and the console died inside the next 250 ms, before the SYNC line. Nothing
  of ours runs in that window: the tram is built from userland primitives, and
  the next ring-0 act would have been the payload call itself. So the last
  build died while the page was merely idle -- right after the staging burst.

  The burst is the suspect. The 642,888-byte copy and the .bss clear ran about
  100,000 times, and each iteration built a fresh int64 for the address and
  another for the value. This int64 class installs ~12 closures on every
  instance, so the burst left millions of short-lived cells behind. The first
  idle collection after that garbage is exactly when 1402zl stopped painting.
  The alternative is an asynchronous kernel path, which no build has caught in
  the act because the page always died before the payload call could report.

  So 1402zm removes the garbage, fires step 1 at the earliest point the screen
  can show it, and puts a clock on the screen that keeps time across a freeze.
  One way or the other, the next run names its cause.

What changed in afterglow-g.js for 1402zm
  - Zero-garbage staging. Both loops mutate one cursor int64 and one word
    int64 in place (add32inplace, direct low/hi writes). The primitive reads
    low/hi and its aim/restore path allocates nothing, so the staging now
    leaves the JS heap as it found it. Same bytes, same order, same result.
  - Fire first, idle later. The 300+250+250+400 ms naps between the gate
    heartbeat and the payload call are gone. The old "idle window spent" line
    is gone with them. After the heartbeat the tram is built straight away,
    the heartbeat / tram / SYNC lines are painted in one 120 ms frame, and the
    call goes out. rc and the table check are painted immediately after the
    return. The two 300 ms early naps (version preset, kernel base line) are
    40 ms each; they only exist to let the log paint.
  - Deadman clock. The status line above the log now reads
        ALIVE <seconds> s  |  <phase>
    and is repainted every 100 ms by its own timer, independently of the log.
    Whatever it shows at a freeze is the last moment the main thread was
    alive; the phase is the last say() that reached it. At the call it reads
        ALIVE 8.41 s  |  FIRE [1] 0x116be
  - The [7b] resolver now prints the live 14.02 bytes at the ORIGINAL 14.00
    offset whenever it shifts a site, e.g.
        [7b] self verification shifted +1152 -> 0x628b04  (0x628684 live ...)
    That is how the next port tells whether the shift found the same
    instruction or a lookalike.
  - [7b] lines are forwarded to ag_log as well (the regex now covers 7b).
  - Post-step idle is four 400 ms heartbeats instead of three 700 ms ones.
  - Patch set and kernel state are UNCHANGED from 1402zl: 8 memcpy-family
    "eb" sites, self verification applied at shifted 0x628b04, delayed panic
    on suspend at 0x62926f, the five dlsym/load_prx sites still SKIPped.
    Both panic-related sites remain applied exactly as last run.

How to read the next crash
  - freeze with the clock at "FIRE [1] 0x116be" and SYNC on screen: the
    payload call was entered and did not come back. That is a ring-0 fault in
    the payload; the last log line names the step.
  - clock stopped at an earlier phase: the page still dies during staging,
    with no payload call made. The clock value says how long after the gate
    it happened -- compare it with the roughly 0.5 s seen on 1402zl after
    the heartbeat.
  - clock still counting, no new log lines: the main thread is alive and
    something else is stuck. Note the value and report it.
  - rc=0 printed, then the console dies during the heartbeats: step 1
    returned and the kernel went down afterwards; the four heartbeats bracket
    the moment.
  - "table[0] ... MISMATCH": the fill did not run as expected; the printed
    value tells which base/offset arithmetic failed.
  - dbgstop run with the clock frozen at STOPPED -- SAFE TO EXIT: normal end.

Kernel-state interlock
  Before any trigger the run asks whether mprotect can add PROT_EXEC to a
  writable mapping. A clean boot refuses it; after a successful run it is
  accepted, and the run stops instead of firing twice into a patched kernel.
  A page reload, a Rest Mode resume or a SceShellUI restart all keep the
  patched kernel; only a full power-off clears it.

  go-check.html   safe check only: prints "... PATCHED" or "... FRESH"
                  with no trigger and no patches
  go-force.html   opt-in bypass for a boot you know is clean (force=1).
                  Firing twice on a patched kernel panics the console.

Do not use on a console you cannot afford to crash; test only with owner
permission. Capture the full on-screen log, including the status line.
