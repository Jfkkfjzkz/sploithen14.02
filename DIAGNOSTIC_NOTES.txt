Diagnostic build 1402zl. Payload binaries and memory offsets are unchanged;
only afterglow-g.js and the entry pages differ from 1402zk. This is one new
ring-0 call per boot, by design.

Why this build exists
  The 1402zk run printed
      [kp] gate heartbeat 0xffffffffccf50000, firing step 1 next
  and the console died ~2 s later, with the SYNC line never painted. Since
  say() paints synchronously and nap() yields to the compositor, the death
  happened either in the 300 ms idle nap after the heartbeat or during the
  host-side trampoline build -- before fire(), not inside the payload.

  The prime suspect is a real port bug now proven from our own 14.02 dump:
  the [7b] resolver searched the shift list for a confirming instruction, and
  when it found none it still let [8] write the 14.00 bytes at the 14.02
  offset. Six sites have no branch there at all, so those writes landed
  mid-instruction:
      0x1b7504  `90 e9` inside a `lea`       -> wild jmp
      0x628684  `eb 00` inside a `lea`       -> bzero buffer pointer corrupted
      0x1b7a53  displacement tail of `je` at 0x1b7a4f -> wild jump
  A system path that touches dlsym/load_prx or self-verification after the
  chain completes would then jump into garbage -- exactly the kind of death
  that arrives a beat after the last painted line.

What changed in afterglow-g.js
  - the patch resolver now builds applyList/skipped:
      * a site already equal to the wanted bytes is applied;
      * a site whose live instruction is a safe jcc is applied -- for "eb"
        any short jcc (0x70..0x7f) of the same length, for "eb04" the same
        short jcc with displacement 0x04, for "90e9" any 0f-prefixed jcc --
        because forcing a branch only requires landing on a branch;
      * otherwise the shift list is searched (16..1280 bytes) for a site
        that does confirm; a hit is applied at the shifted address;
      * otherwise the site is SKIPped, never written, and its 12 live bytes
        are printed: [7b] SKIP <name> @0x<off> live <hex>.
  - [8] verifies applyList only and prints "N of N confirmed kernel patches
    in place". N can be less than 15; that is the fix, not a failure.
  - two paint checkpoints were inserted so the silent stretch after the gate
    heartbeat is split into named windows:
      [kp] idle window spent, building tram      (+ 250 ms nap)
      [kp] tram built (<n> bytes), firing now    (+ 250 ms nap)
  - unchanged from 1402zk: probe bypass (image+0x98488 preset to 0x57a,
    0x116be called directly with edi=0x57a), no patchset.bin, no paddingRW
    pde write, no planted string, no kernel-padding stack switch, payload on
    the syscall's own kernel stack, KP_MAX_STEPS=1, exact step-1 checks
    (rc=0, version word 0x57a, table[0] == kbase+0x1c0).

How to read the next crash (if there is one)
  - last line "gate heartbeat ... firing step 1 next": death in the 300 ms
    idle nap. The kernel is unstable without any payload call and with no
    blind patch writes -- report it, this narrows the hunt to the gate itself.
  - last line "idle window spent, building tram": death while writing the
    trampoline/marker words from the host. The host primitive is the suspect.
  - last line "tram built (...), firing now": death in the 250 ms window
    before the syscall. Nothing new ran; that points at residual kernel state.
  - last line "SYNC entering [1]": the first payload call faulted in ring 0.
    Report the exact rc/mismatch line if one appears.
  - death during "idle heartbeat 1..3": step 1 returned but left the kernel
    unstable -- that points at the table contents, not at the call.
  - "table[0] ... MISMATCH": the fill did not run as expected; the printed
    value tells which base/offset arithmetic failed.
  - a SKIP line with surprising live bytes is useful too: it pins down where
    the 14.02 code moved relative to 14.00.

Kernel-state interlock
  Before any trigger the run asks whether mprotect can add PROT_EXEC to a
  writable mapping. A clean boot refuses it; after a successful run it is
  accepted, and the run stops instead of firing twice into a patched kernel.
  A page reload, a Rest Mode resume or a SceShellUI restart all keep the
  patched kernel; only a full power-off clears it.

  go-check.html   safe check only: prints "... PATCHED" or "... FRESH"
                  with no trigger and no patches
  go-force.html   opt-in bypass for a boot you know is clean (force=1).
                  Firing twice on a patched kernel panics the console.

Do not use on a console you cannot afford to crash; test only with owner
permission. Capture the full on-screen log.
