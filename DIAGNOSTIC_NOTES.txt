Diagnostic build 1402zk. Payload binaries and memory offsets are unchanged;
only afterglow-g.js and the entry pages differ from the previous zip. This is
one new ring-0 call per boot, by design.

Why this build exists
  The previous run completed the kernel chain, the patch set, the padding pde
  write and the version-probe redirect, printed
      [kp] version probe aimed at 0xffffffff8b933000
  and then the console died in the 400 ms idle window that follows -- before
  the trampoline was even built, i.e. before any kpayload call was fired. Two
  suspects remain: (a) the pde write / RELRO plant machinery itself, and
  (b) the 641-byte patchset's 0x125791 block, whose writes decode as
  incoherent code at the 14.02 sites in our own kernel dump. 1402zk removes
  both from the path and tests one new thing only: step 1 of the kpayload.

What changed in afterglow-g.js
  - probe BYPASS, not redirect: 0x115be (the "s/release_" scan) early-outs
    whenever the word at image+0x98488 is nonzero, and 19 payload sites call
    it. The build presets that word to 0x57a in userland and calls the table
    fill 0x116be directly with edi=0x57a -- byte for byte the continuation a
    successful probe produces. The scan window that starts in the unmapped
    hole at base+0x1300000 is never read.
  - runPatchSet, paddingRW, the planted version string, the two scan-patch
    writes and the switch to the RELRO padding as a ring-0 stack are all
    skipped. The payload call runs on the syscall's own kernel stack with rsp
    aligned to 16 and the old rsp parked in the 16 bytes below the call.
  - KP_MAX_STEPS=1: step 1 is 0x116be (the old 0x11bd1 entry minus its probe
    prelude). After it returns, STATE.haltChain stops the chain before the
    debug-settings pass, and three idle heartbeats print over ~2.6 s.
  - step 1 result is checked exactly: rc must be 0, word 0x98488 must still be
    0x57a, and table[0] at image+0x986f8 must equal kbase+0x1c0 (the first
    dword of the 14.02 fill is 0x1c0).
  - a gate heartbeat (k.base(), the same body every k.read/k.write already
    ran) is printed immediately before the fire.

How to read the next crash (if there is one)
  - last line before "SYNC entering [1]": the console died in an idle window
    with no payload call yet. The pde/plant/patchset removal was not enough;
    the instability is in the state afterglow itself leaves behind.
  - last line is "SYNC entering [1]" (after its 400 ms paint window): the
    first payload call faulted in ring 0. Report the exact rc/mismatch line if
    one appears.
  - death during "idle heartbeat 1..3": step 1 returned but left the kernel
    unstable -- that points at the table contents, not at the call.
  - "table[0] ... MISMATCH": the fill did not run as expected; the printed
    value tells which base/offset arithmetic failed.

Kernel-state interlock
  Before any trigger the run asks whether mprotect can add PROT_EXEC to a
  writable mapping. A clean boot refuses it; after a successful run it is
  accepted, and the run stops instead of firing twice into a patched kernel.
  A page reload, a Rest Mode resume or a SceShellUI restart all keep the
  patched kernel; only a full power-off clears it.

  go-check.html   safe check only: prints "... PATCHED" or "... FRESH"
                  with no trigger and no patches
  go-force.html   opt-in bypass for a boot you know is clean (force=1).
                  Firing twice on a patched kernel panics the console.

Do not use on a console you cannot afford to crash; test only with owner
permission. Capture the full on-screen log.
