Diagnostic build 1402zm. Payload binaries and memory offsets are unchanged;
only afterglow-g.js and the entry pages differ from 1402zl. This is still one
new ring-0 call per boot, by design.

Why this build exists
  The 1402zl run printed
      [kp] tram built (82 bytes), firing now
  and the console died inside the next 250 ms, before the SYNC line. Nothing
  of ours runs in that window: the tram is built from userland primitives, and
  the next ring-0 act would have been the payload call itself. So the last
  build died while the page was merely idle -- right after the staging burst.

  The burst is the suspect. The 642,888-byte copy and the .bss clear ran about
  100,000 times, and each iteration built a fresh int64 for the address and
  another for the value. This int64 class installs ~12 closures on every
  instance, so the burst left millions of short-lived cells behind. The first
  idle collection after that garbage is exactly when 1402zl stopped painting.
  The alternative is an asynchronous kernel path, which no build has caught in
  the act because the page always died before the payload call could report.

  So 1402zm removes the garbage, fires step 1 at the earliest point the screen
  can show it, and puts a clock on the screen that keeps time across a freeze.
  One way or the other, the next run names its cause.

What changed in afterglow-g.js
  - Zero-garbage staging. Both loops mutate one cursor int64 and one word
    int64 in place (add32inplace, direct low/hi writes). The primitive reads
    low/hi and its aim/restore path allocates nothing, so the staging now
    leaves the JS heap as it found it. Same bytes, same order, same result.
  - Fire first, idle later. The 300+250+250+400 ms naps between the gate
    heartbeat and the payload call are gone. The old "idle window spent" line
    is gone with them. After the heartbeat the tram is built straight away,
    the heartbeat / tram / SYNC lines are painted in one 120 ms frame, and the
    call goes out. rc and the table check are painted immediately after the
    return. The two 300 ms early naps (version preset, kernel base line) are
    40 ms each; they only exist to let the log paint.
  - Deadman clock. The status line above the log now reads
        ALIVE <seconds> s  |  <phase>
    and is repainted every 100 ms by its own timer, independently of the log.
    Whatever it shows at a freeze is the last moment the main thread was
    alive; the phase is the last say() that reached it. At the call it reads
        ALIVE 8.41 s  |  FIRE [1] 0x116be
  - The [7b] resolver now prints the live 14.02 bytes at the ORIGINAL 14.00
    offset whenever it shifts a site, e.g.
        [7b] self verification shifted +1152 -> 0x628b04  (0x628684 live ...)
    That is how the next port tells whether the shift found the same
    instruction or a lookalike.
  - [7b] lines are forwarded to ag_log as well (the regex now covers 7b).
  - Post-step idle is four 400 ms heartbeats instead of three 700 ms ones.
  - Patch set and kernel state are UNCHANGED from 1402zl: 8 memcpy-family
    "eb" sites, self verification applied at shifted 0x628b04, delayed panic
    on suspend at 0x62926f, the five dlsym/load_prx sites still SKIPped.
    Both panic-related sites remain applied exactly as last run.

How to read the next crash
  - freeze with the clock at "FIRE [1] 0x116be" and SYNC on screen: the
    payload call was entered and did not come back. That is a ring-0 fault in
    the payload; the last log line names the step.
  - clock stopped at an earlier phase: the page still dies during staging,
    with no payload call made. The clock value says how long after the gate
    it happened -- compare it with 1402zl's roughly 0.5 s after the heartbeat.
  - clock still counting, no new log lines: the main thread is alive and
    something else is stuck. Note the value and report it.
  - rc=0 printed, then the console dies during the heartbeats: step 1
    returned and the kernel went down afterwards; the four heartbeats bracket
    the moment.
  - "table[0] ... MISMATCH": the fill did not run as expected; the printed
    value tells which base/offset arithmetic failed.

Kernel-state interlock
  Before any trigger the run asks whether mprotect can add PROT_EXEC to a
  writable mapping. A clean boot refuses it; after a successful run it is
  accepted, and the run stops instead of firing twice into a patched kernel.
  A page reload, a Rest Mode resume or a SceShellUI restart all keep the
  patched kernel; only a full power-off clears it.

  go-check.html   safe check only: prints "... PATCHED" or "... FRESH"
                  with no trigger and no patches
  go-force.html   opt-in bypass for a boot you know is clean (force=1).
                  Firing twice on a patched kernel panics the console.

Do not use on a console you cannot afford to crash; test only with owner
permission. Capture the full on-screen log, including the status line.
