How mode=dbgstop is meant to end
  On success the screen shows, in order:
      ...normal chain lines...
      [8] N of N confirmed kernel patches in place
      [9] jailbroken, uid 0
      [10] kernel interface is live -- ... handles held open
      [t] ... teardown lines, then "handles defused"
      debug menu enabled -- go to Settings
      [gate] syscall 11 disarmed -- sy_call restored to 0xffffffff9...
      ========================================
        DEBUG MENU PATCH CONFIRMED -- SAFE STOP
        Open Settings and look for Debug Settings.
        No payload was loaded; nothing else will run.
        The syscall-11 gate is disarmed too -- exit is safe.
        You can close the browser now. Cold boot when done.
      ========================================
  and the status line freezes at "STOPPED -- SAFE TO EXIT".
  That is the whole run. The page then does nothing at all.

  What to check on the console
    1. Status line reads STOPPED -- SAFE TO EXIT and the [gate] line names a
       0xffffffff9... address.
    2. Open Settings and look for the Debug Settings entry (usually at the
       bottom of the Settings list on a patched 14.02).
    3. Come back to the browser, close it with the normal buttons.
    4. Report what you saw. If it still panics on exit, syscall 11 was not the
       cause -- send the full log, including the [gate] line.

  If the patch did not stick you get
      [dbg] rcmgr patch write did not stick
      [dbg] DEBUG MENU PATCH FAILED -- nothing more will run
      status "STOPPED -- PATCH FAILED"
  and nothing else; the gate is still disarmed, so exit stays safe.

  If the gate could not be restored (no stash, bad pointer, write did not
  stick) the banner says "WARNING: the syscall-11 gate is still armed" and
  the status freezes at "STOPPED -- GATE STILL ARMED". The debug menu patch
  is still in place; only browser exit is risky.

Expected chain lines (unchanged from 1402zm)
  [7b] N sites confirmed, M left untouched
  [7b] SKIP <name> @0x<off> live <12 bytes>       (one per untouched site)
  [7b] <name> shifted +<n> -> 0x<off+n>  (0x<off> live <6 bytes>)
  [8] N of N confirmed kernel patches in place
  A smaller N than 15 is normal and correct -- the skipped sites are the ones
  the firmware moved, and writing them blind is what killed the 1402zk run.

How to read the next crash
  - clock "ALIVE ... | FIRE [1] 0x116be" and SYNC on screen: a ring-0 call
    was entered and did not come back; the last log line names the step.
    (kpstep path only; dbgstop never fires the payload.)
  - clock stopped at an earlier phase, before the rcmgr pass: the page died
    during the chain; the phase names the last line that got there.
  - clock keeps counting but no new log lines: the main thread is alive and
    something else is stuck. Note the value and report it.
  - clock frozen at "STOPPED -- SAFE TO EXIT" is the normal end of dbgstop.
  - clock frozen at "STOPPED -- GATE STILL ARMED": the rcmgr work finished
    but the gate could not be put back; do not close the page, power off.

Kernel-state interlock
  Before any trigger the run asks whether mprotect can add PROT_EXEC to a
  writable mapping. A clean boot refuses it; after a successful run it is
  accepted, and the run stops instead of firing twice into a patched kernel.
  A page reload, a Rest Mode resume or a SceShellUI restart all keep the
  patched kernel; only a full power-off clears it.

  go-check.html   safe check only: prints "... PATCHED" or "... FRESH"
                  with no trigger and no patches
  go-force.html   opt-in bypass for a boot you know is clean (force=1)

One armed run per boot. Full power cycle between attempts - a reload says
"this kernel is already open / Not firing again".
