What 1402zm changes (details in DIAGNOSTIC_NOTES.txt)
  - ZERO-GARBAGE STAGING. The 642,888-byte copy and the .bss clear built a
    fresh int64 for the address and for the value every 8 bytes, about 100k
    iterations. This int64 class installs ~12 closures per instance, so the
    burst left millions of short-lived cells, and the first idle collection
    after it is exactly where 1402zl stopped painting. Both the cursor and the
    word are now mutated in place; the primitive reads low/hi and its own
    path allocates nothing.
  - FIRE FIRST, IDLE LATER. 1402zl spent 300+250+250+400 ms in naps between
    the gate heartbeat and the call. 1402zm builds the tram straight after
    the heartbeat and lets a single 120 ms frame paint the heartbeat, tram
    and SYNC lines, then calls. rc is painted immediately after the return.
  - DEADMAN CLOCK in the status line, "ALIVE <s> | <phase>", repainted every
    100 ms by its own timer. Whatever it shows at a crash is the last moment
    the main thread was alive; the phase names the last line that got there.
  - Shifted patches print the live bytes at the ORIGINAL 14.00 offset, and
    [7b] lines now reach the server log (ag_log).
  - Kernel work identical to 1402zl: probe bypass (word at image+0x98488
    preset to 0x57a, 0x116be called directly with edi=0x57a), no patchset.bin,
    no paddingRW pde write, no planted string, no kernel-padding stack switch,
    payload runs on the syscall's own kernel stack, KP_MAX_STEPS=1.

Expected patch lines
  [7b] N sites confirmed, M left untouched
  [7b] SKIP <name> @0x<off> live <12 bytes>       (one per untouched site)
  [7b] <name> shifted +<n> -> 0x<off+n>  (0x<off> live <6 bytes>)
  [8] N of N confirmed kernel patches in place
  A smaller N than 15 is normal and correct -- the skipped sites are the ones
  the firmware moved, and writing them blind is what killed the 1402zk run.

How to read the next crash
  - clock "ALIVE ... | FIRE [1] 0x116be" and SYNC on screen: the payload call
    was entered and did not come back -- a ring-0 fault inside the payload,
    and the last log line names the step.
  - clock stopped at an earlier phase, before FIRE: the page still dies
    during staging with no payload call made; the value says how long after
    the gate it happened.
  - clock keeps counting but no new log lines: the main thread is alive and
    something else is stuck. Note the value and report it.
  - rc=0 printed, then the console dies during the heartbeats: step 1
    returned and the kernel went down afterwards. The four heartbeats bracket
    when.

Kernel-state interlock
  Before any trigger the run asks whether mprotect can add PROT_EXEC to a
  writable mapping. A clean boot refuses it; after a successful run it is
  accepted, and the run stops instead of firing twice into a patched kernel.
  A page reload, a Rest Mode resume or a SceShellUI restart all keep the
  patched kernel; only a full power-off clears it.

  go-check.html   safe check only: prints "... PATCHED" or "... FRESH"
                  with no trigger and no patches
  go-force.html   opt-in bypass for a boot you know is clean (force=1)

One armed run per boot. Full power cycle between attempts - a reload says
"this kernel is already open / Not firing again".
